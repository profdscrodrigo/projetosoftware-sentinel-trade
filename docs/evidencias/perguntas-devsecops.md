# Perguntas reflexivas da esteira DevSecOps — respostas e evidências

O enunciado lista perguntas para nos questionarmos. Respondemos cada uma e indicamos onde o projeto comprova a resposta.

| # | Pergunta | Resposta no SentinelTrade | Onde verificar |
|---|---|---|---|
| 1 | Quais dados entram neste componente e qual regra valida cada um? | Toda entrada vira texto bruto (`SolicitacaoOrdem`) e passa por `Validacoes`: ticker `^[A-Z]{4}[0-9]{1,2}$`, quantidade 1–1.000.000 inteira, preço ≤ 2 casas e ≤ R$ 1.000.000, chave `[A-Za-z0-9_-]{16,64}`, lado COMPRA/VENDA, e-mail, nome, senha. | `Validacoes`, `ValidacoesTest` |
| 2 | Uma entrada manipulada pode causar injeção, execução indevida, vazamento ou indisponibilidade? | Injeção SQL: impossível por construção (`PreparedStatement`; 0 concatenações; 45 comandos conferidos). Log forging/ANSI: `Sanitizador`. Indisponibilidade: limites de tamanho, de frequência e de tentativas. Sem `eval` nem comandos/arquivos construídos da entrada. Na API: corpo ≤ 16 KB, JSON plano com campos permitidos, caminho sem `..`/`%`; no front-end, nada é inserido como HTML (CSP proíbe script inline). | `Jdbc`, `ServidorWeb`, `validacao-sql.txt`, `ServidorWebTest`, demo §14 |
| 3 | Quem pode executar esta ação e como a autorização é validada no servidor? | Todo caso de uso começa em `AutenticacaoService.exigir(token, papéis…)`; a interface só repassa o token. Negações são auditadas. | `AutenticacaoServiceTest`, `AdministracaoRiscoTest` |
| 4 | O usuário tem apenas as permissões estritamente necessárias? | 3 perfis disjuntos; investidor não vê dados alheios (identidade vem da sessão); no banco, o papel `sentinel_app` não tem `UPDATE/DELETE` na auditoria. | `PrivacidadeEAcessoTest`, `hardening-postgres.sql` |
| 5 | Quais dados são sensíveis e onde ficam armazenados, transmitidos e registrados? | Senha: só hash PBKDF2. Token de sessão: só SHA-256 no banco. Segredo MFA: no banco, **cifrado com AES-256-GCM** (a chave vem de `MFA_ENCRYPTION_KEY`, fora do banco; **risco residual:** em produção a chave deve ficar em KMS/HSM e há que planejar rotação). Logs e auditoria nunca recebem senha/token/segredo. | `Pbkdf2Hasher`, `CifradorSegredo`, `schema.sql`, `CifradorSegredoTest`, `AutenticacaoServiceTest.falhasDeLogin…` |
| 6 | Há credenciais, chaves ou tokens expostos no código, repositório, configuração ou logs? | O projeto mantém os segredos de execução em `.env`, que é ignorado pelo Git; `.env.example` contém apenas nomes de variáveis, `seed.sql` não contém usuários e as senhas de demonstração podem ser geradas em tempo de execução. A esteira configura *gitleaks* com histórico completo em cada `push`/`pull_request`; ainda não executamos essa varredura no GitHub Actions; vamos registrar o resultado depois do `push`. | `.gitignore`, `.env.example`, `.github/workflows/ci.yml` |
| 7 | O tratamento de erro revela informações úteis a um atacante? | Exceções de domínio têm mensagem segura; erro inesperado mostra só uma referência e vai ao log; erros de banco viram "Erro ao acessar o banco de dados"; login com mensagem única. | `Excecoes`, `CliApp`, `TransacaoJdbc.traduzir` |
| 8 | As dependências têm vulnerabilidades conhecidas ou estão desatualizadas? | Só 2 dependências (driver PostgreSQL e JUnit); núcleo usa apenas o JDK. Perfil Maven `seguranca` roda OWASP Dependency-Check e falha com CVSS ≥ 7. | `pom.xml`, `ci.yml` |
| 9 | O código passou por revisão e testes para cenários inválidos, abusivos e não autorizados? | 169 testes automatizados Maven executados em 26/11/2026 (167 testes das demais classes + 2 testes de integração contra PostgreSQL; 0 falhas, 0 erros e 0 ignorados), além do teste de interface em navegador, boa parte de cenários **negativos**: entradas maliciosas, acesso cruzado, perfis errados, reenvios, falhas externas, adulteração da auditoria. | `resultado-testes-maven-postgresql-2026-11-26.txt` |
| 10 | O pipeline bloqueia vulnerabilidades críticas, segredos expostos e dependências inseguras? | Configurado em `ci.yml`: build/testes com PostgreSQL de serviço, *gitleaks* e OWASP Dependency-Check com bloqueio em CVSS ≥ 7. Executamos localmente os 169 testes. Ainda não publicamos esta versão nem verificamos a execução remota do workflow; por isso, não registramos os jobs do GitHub Actions como aprovados. | `.github/workflows/ci.yml` |
| 11 | Como o sistema reage à indisponibilidade ou resposta malformada de uma API externa? | *Timeout*, *circuit breaker*, fila, recuo exponencial, revalidação de todo dado externo, descarte auditado de relatório inválido, degradação controlada de cotações. | `CorretoraResiliente`, `CotacaoService`, demo §10–11 |
| 12 | Há logs de auditoria, monitoramento, alerta, rollback e resposta a incidentes? | **Implementamos auditoria** imutável e verificável e **rollback transacional** no banco. **Ainda não implementamos monitoramento, alertas ou resposta automatizada a incidentes**; como evolução, podemos expor métricas de `CorretoraResiliente.estado()` e a contagem de `ANOMALIA_EXECUCAO`. | `AuditoriaService`; lacuna declarada |
